1. Week2 结束时系统的问题

黑盒化与不可观测：一次回答可能包含推理、搜索和多次工具调用，系统只有 Session 和 Message，无法跟踪中间的微观步骤与故障点。

状态易失：所有运行状态保存在内存 dict 中，进程重启或崩塌会导致上下文和正在执行的任务彻底丢失。

缺乏容错与恢复机制：请求中途断线或超时后，任务直接挂死，无法“读档”续传，只能让用户重头开始。

单机并发瓶颈：多 Worker 部署时遭遇“内存割裂”与竞态冲突，无法实现分布式节点协作。

2. 为什么引入 AgentRun

普通聊天是单次“一问一答”（I/O），而 Agent 是长达数分钟的“多步推理与物理执行过程”。
AgentRun 将执行过程抽象为独立的实体，成为任务生命周期的唯一载体。它把“过程状态”（如 waiting_tool）与“结果状态”（Message.status）彻底解耦，为流式推送、暂停/恢复、限流降级和急停控制提供了确切的操作句柄。

3. 为什么 RunStep 和 ToolCallRecord不能只依赖日志

文本日志是“非结构化死数据”：只能用于运维事后看文本，无法通过 SQL 进行高效的维度统计（如：某工具过去 24 小时的平均耗时、失败率、Token 成本）。

驱动不了系统逻辑：状态机切换、前端步骤进度条渲染、断点重试依赖结构化的数据字段，而不是正则表达式解析日志。

缺乏合规与审计能力：工具调用触碰物理世界（写库、扣款），需要结构化的 ToolCallRecord 实施严格的入参脱敏与权限审计。

4. 为什么数据库必须成为 Source of Truth

内存是易失（Volatile）且单机孤岛化的。生产环境下服务器随时的滚动更新、OOM 崩溃或分布式多 Pod 部署，决定了内存绝不能承担最终承诺。
持久化数据库（PostgreSQL 等）通过 ACID 特性提供权威、全局唯一、跨节点共享与永久可追溯的事实源（SoT），内存退居为高频 I/O 的临时水箱与 L1 缓存。

5. Checkpoint 和 RunStep 的区别

维度	RunStep	Checkpoint
主要目的	微观轨迹留痕（为了看与审计）	确定性状态快照（为了用与复活）
写入特征	包含增量中间态（可能包含吐了一半的 Thought 或报错）	仅在关键稳定节点刷盘，经过数据清洗与格式化
反序列化	仅作为历史树展示	引擎直接载入反序列化，以此恢复 LLM 上下文

6. Resume 和 Regenerate 的区别

Resume（恢复执行）：从最近的稳定 Checkpoint 加载状态，跳过已完成的步骤，创建一个子 Run（继承 parent_run_id）继续向下跑。

Regenerate（重新生成）：放弃此前所有的中间推演与工具执行结果，回到最初的用户 Prompt，从 Step 1 干净地开启一个全新的 Run。

7. Heartbeat 为什么不能由 AgentEvent 替代

AgentEvent（业务驱动）：由大模型或工具触发（如吐字、调用），频率极不稳定。调慢速第三方 API 时，可能 30 秒没有任何 Event 产生，但进程依然健康。

Heartbeat（时钟驱动）：固定频率（如每 5 秒）由独立线程/连接强制刷盘。它是衡量物理进程存活的唯一标准，与业务进度无关。

8. Stale Run 是什么

Stale Run（僵尸任务）是指在数据库中物理状态依然显示为 running 或 waiting_tool，但由于宿主机宕机、OOM 杀进程或网络断连，导致 last_heartbeat_at 已长期停止更新的任务。它是生产环境中典型的“名存实亡”垃圾状态。

9. Transaction 为什么重要

Agent 的一次状态变更涉及多表联动（例如：创建 AgentRun + 写入初始 RunStep + 更新 Session 状态）。
事务（Transaction）提供了 ACID 原子边界：确保这些操作“要么全部成功提交（Commit），要么全部撤销（Rollback）”，彻底消除数据库中只有 Run 没有 Step 的破坏性垃圾碎片。

10. Idempotency 为什么必须依赖数据库约束

代码层的“先查后写”（if not exists）在并发请求下存在严重的竞态条件（Race Condition），两个完全相同的请求在同毫秒打入会同时通过检查。
唯有在数据库层面设置 UNIQUE(idempotency_key) 索引，依靠存储引擎底层的排他锁与唯一性校验，才是拦截重复提交与重复副作用的终极物理铁闸。

11. 当前系统仍有哪些不足

锁与任务分配单机化：目前并发锁与任务调度仍依赖单机内存或简单表锁，缺乏 Redis 分布式锁与专业消息队列（MQ）的解耦。

流式写库压力：大模型高频吐字时，若直接频繁写库会导致 DB 连接池暴涨与磁盘 I/O 瘫痪。

缺乏长任务异步后台解耦：Agent 执行仍占据 Web 服务的 Request/Response 异步线程，尚未完全剥离为独立后台 Worker 进程。

12. Week4 为什么需要异步任务与并发

在长任务 Agent 场景下，单个请求执行可能长达数分钟。 Week 4 必须引入异步任务队列（如 Celery / Arq / Temporal）与高并发控制：

解耦 Web 与 Worker：HTTP 接口仅负责接收请求、校验幂等并投递任务，立即可靠响应，将耗时的 Agent 循环丢给后台 Worker 节点。

支撑高并发与横向扩展：通过消息队列实现集群动态扩容、任务抢占、平滑限流以及工具并发调用（Parallel Tool Calling），彻底破除单机并发上限。
