# Day18：Repository 替换内存 Store

## 今日主题

让数据库逐步成为 Agent 状态的 Source of Truth。

---

## 卡片 1：Source of Truth 是什么？

Source of Truth 是系统认定的最终可信数据来源。

我的理解：
在复杂架构里，数据可能同时存在于浏览器 LocalStorage、Redis 缓存、服务器内存和 PostgreSQL 数据库中。当各处的数据因为网络延迟或服务重启出现不一致时，系统必须无条件信任 SoT。在生产级 Agent 架构中，持久化数据库（如 PostgreSQL）就是权威的 SoT。任何内存中的状态都只是 SoT 的临时副本（Replica）或投影（Projection）。

---

## 卡片 2：为什么内存不能作为生产事实来源？

内存会因为进程重启丢失，多 worker 之间也不共享。

我的理解：
把状态存在 Python 内存 dict 里有两个致命死穴：
物理易失性：一旦触发代码部署、容器重启或 OOM 崩溃，所有用户正在运行的 Agent 任务和聊天记录会全部蒸发。
无法横向扩展（Scale-out）：生产环境通常会跑多份副本（如 K8s 中的多个 Pod 或 Uvicorn 的多 Worker 进程）。请求 A 打到进程 1 把状态写入了进程 1 的内存，下一个请求 B 打到进程 2，进程 2 的内存里一片空白，系统瞬间遭遇“分裂脑（Split-brain）”问题。

---

## 卡片 3：内存 Store 现在还保留什么价值？

运行时锁、临时缓存、当前请求中的状态辅助。

我的理解：
把 SoT 交给数据库，并不意味着要完全摒弃内存。在大模型高频吐出 SSE Token 的极速流式阶段，如果每一个 Token 片段都直接写一次 DB，数据库连接池瞬间就会被拖垮。此时，内存变成了缓冲水箱：流式生成时在内存中高频更新，生成完毕或阶段性 Step 完成时再批量冲刷（Flush）到 DB，兼顾了极致的响应速度与数据的最终一致性。

---

## 卡片 4：Repository 的职责是什么？

Repository 隔离业务逻辑和数据库读写细节。

我的理解：
它遵循面向对象设计的依赖倒置原则（DIP）。Agent 引擎只向 Repository 提出声明式诉求（例如 save_run()、get_session_history()），而完全不需要关心底层是用 SQLAlchemy 写 PostgreSQL，还是用 asyncpg 执行原生 SQL。这种隔离保证了未来即便是将存储介质更换为 Redis 或 MongoDB，上层的 Agent 业务状态机代码也不需要修改哪怕一行。

---

## 卡片 5：为什么 API 层不应该直接返回 ORM？

ORM 是数据库结构，API 应该返回业务模型或响应模型。

我的理解：
ORM 模型是死死绑定在数据库物理 Session 上的实体。如果直接把它丢给 FastAPI 返回：

泄露内部隐私：数据库中的软删除标记、租户隔离字段、密码哈希等内部细节可能会被意外暴露给前端。

惰性加载（Lazy Loading）崩溃：在 HTTP 响应序列化时，访问未预加载的关系字段会触发 DetachedInstanceError 报错。

破坏架构边界：数据库表加个字段，前端 API 接口结构跟着变，彻底丧失了系统的防腐层。

---

## 卡片 6：ORM → Pydantic 转换解决什么问题？

把数据库对象转换为业务对象，隐藏数据库字段细节。

我的理解：
通过在 Pydantic 模型中配置 model_config = ConfigDict(from_attributes=True)，我们建立了一条从“数据库物理实体”到“业务数据传输对象”的单向清洗流水线。ORM 对象从 DB 读出后，立刻被转译为纯净的 Pydantic 模型。这不仅斩断了 SQLAlchemy Session 的附身羁绊，还可以安全地在 API 边缘进行字段过滤、格式转换（如 UTC 时间转 ISO 字符串）和敏感数据脱敏。
---

## 卡片 7：为什么 Day18 先改查询，再彻底改写入？

写入链路已经在 Day17 开始双写。  
Day18 重点是让服务重启后仍能查询历史。

我的理解：
Day 17 我们已经打通了异步双写通道，而 Day 18 优先把查询链路（Read Path）重构为从 DB 读取，可以第一时间验证“服务重启后，历史会话与运行轨迹是否依然可回放”。先确保读路径的正确性与 Schema 兼容性，在确认系统能稳定从数据库“吸取营养”后，再安全地下线内存写入，能最大程度降低架构升级时的系统风险。

---

## 卡片 8：ToolCallRecord 为什么要落库？

工具调用记录用于性能分析、失败排查、安全审计和成本统计。

我的理解：
LLM 吐出的文本只是无害的字符串，但工具（Tool）会真正去查数据库、发邮件、扣减用户余额。将 ToolCallRecord 结构化落库，不仅能在出事时快速复盘（如：第 3 步 Agent 到底传了什么危险参数给 SQL 执行工具），还能帮助运维分析哪个第三方 API 拖慢了响应，甚至精准计算出每次 AgentRun 消耗的外网工具调用成本。

---

## 卡片 9：为什么锁暂时还用内存？

分布式锁更复杂，需要 Redis 或数据库锁。  
Day18 先保持当前单进程内的并发保护。

我的理解：
完美的分布式锁（如基于 Redis 的 Redlock 或 PostgreSQL Advisory Lock）涉及网络分区、锁超时续期、死锁检测等复杂的分布式难题。在 Day 18 这个节点，我们的核心战役是完成数据持久化。在单进程/单 Worker 阶段，继续使用 Python 内存锁（如 asyncio.Lock）保护并发会话，能让我们把注意力集中在数据库 Repository 的无缝替换上。架构演进切忌贪多，步步为营才是正道。

---

## 卡片 10：Day18 和 Day19 的关系

Day18 让数据库成为查询事实来源。  
Day19 将在此基础上设计中断恢复和 run resume。

我的理解：
如果数据库里没有保存完整的 AgentRun 状态和 RunStep 步骤轨迹（Day 18 的成果），那么当系统崩溃或网络中断时，新启动的进程对过去发生的事情将一无所知。Day 18 保证了 Agent 的每一步思考都有据可查，才让 Day 19 能够从数据库中重新加载（Rehydrate）未完成的 Run，实现长任务的中断恢复与容错重启！
